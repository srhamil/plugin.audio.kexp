================================================================================
1. WHAT THIS IS
================================================================================
Kodi audio add-on (plugin.audio.kexp, v0.1.0 BETA, provider
srhamil, GPL-3.0-or-later): KEXP 90.3 Seattle live stream + the
station's public TWO-WEEK ARCHIVE, browsable by day / program / host,
with now-playing metadata REPLAYED IN SYNC during archive playback.
Companion reference: kexp-archive-api.md (the reverse-engineered API
map, curl-verified 2026-07-19/20) -- read it alongside this.

Origin: spun out of plugin.audio.internetradio (which keeps its own
live-KEXP station). Built by porting that add-on's validated
architecture; it is the parent design. Same target environment as all
of Simon's audio add-ons: RPi4 + DAC appliance, Kodi 21 Omega on
LibreELEC, Aeon Nox SiLVO, Bravia/CEC, stdlib only. Same owner
workflow rules: design discussion before code, complete
compile-checked file deliverables, type hints, new-format settings.xml
+ strings.po, log prefixes [plugin.audio.kexp/plugin|/service|/data],
verbose INFO during shakedown then LOGDEBUG.

STATUS: v0.0.1 generated 2026-07-20 as a no-further-input prototype at
Simon's request (design-discussion rule explicitly waived for that
round). v0.0.2 followed the same day after the first device test:
findings #1-#5 below fixed in one pass, compile-checked + logic
smoke-tested off-device. BROWSING partially device-tested (shows list
built; see #1). ARCHIVE PLAY/SEEK and the /v2/plays airdate sync are
STILL UNPROVEN ON DEVICE -- the first test crashed on browse before
reaching playback. Simon's tree becomes source of truth the moment he
touches it.

2. ARCHITECTURE
================================================================================
* default.py -- plugin/router. Root: "Listen live" (stream URL as item
  path, property kexp_mode=live -- the internetradio pattern
  unchanged) + folders Shows by day / Programs / DJs (user-facing
  "DJs"; code/API/action strings stay "host*" to match KEXP's own
  vocabulary). ALL folder listings use setContent("albums") (view-mode
  lesson from internetradio) so SiLVO offers wall/grid views. Shows-by-
  day cells carry a composited date-card PNG thumb (kexpdata.day_tile):
  Kodi's runtime art decoder has NO SVG handler on Omega/LibreELEC ("Could
  not find suitable input format: image/svg+xml") and there is no image/
  font lib in Kodi's Python, so date cards are built by STACKING pre-
  rendered PNG STRIPS with stdlib zlib+struct (splice raw scanlines).
  Strips ship per language under resources/media/datestrips/<lang>/
  (12 month + 31 day + 7 weekday PNGs, 400px wide, 8-bit RGB no-alpha, +
  labels.json); en-gb is the shipped default that ISO code "en" maps to,
  and the universal fallback. Composites cached in profile/date_tiles/ as
  tile-<lang>-<MON>-<DD>-<WKD>.png (localized-content names: cache-clean +
  collision-free across languages). Strips are currently PLAIN BLACK TEXT
  ON WHITE. DJ cells use the DJ's photo (image_uri) as thumb + name in
  label/tag + most-frequent program as label2 (setAlbum/setArtist) -- the
  earlier SVG "name burned into photo" card was abandoned for the same
  no-SVG-decoder reason. Show-row labels are context-
  trimmed: day folder = "HH:MM Program with DJ"; program folder =
  "Wkd Mon DD  HH:MM  with DJ"; DJ folder = "Wkd Mon DD  HH:MM
  Program". The player info-tag title always keeps the full show name.
  ARCHIVE PLAYBACK RESOLVES AT PLAY TIME via setResolvedUrl -- the
  family's first deliberate departure from the no-resolve-handler
  rule, for API frugality (each URL costs a get_streaming_url call;
  resolving at listing time would burn 6-8 per folder). The resolved
  item gets kexp_mode=archive, setMimeType("audio/mpeg") +
  setContentLookup(False) (skip Kodi's probe = no wasted AIS session).
* resources/lib/kexpdata.py -- data layer: get_json (GET only; the
  API 405s HEAD), fetch_shows() (paginates /v2/shows/?ordering=
  -start_time&limit=100 until results age past 14 days, max 12 pages,
  15-min disk cache in profile/shows_cache.json), group_by_day /
  unique_programs / unique_hosts (client-side slicing of the one
  cached list -- avoids unverified server filter params entirely),
  resolve_stream() (get_streaming_url wrapper), write_session/
  read_session (profile/archive_session.json plugin->service handoff),
  day_tile() (composites cached PNG date cards from shipped strips; see
  the Shows-by-day note above). NOTE: default.py parses its own
  YYYY-MM-DD day keys via a manual int-split, NOT datetime.strptime --
  strptime lazily imports _strptime and Kodi's per-invocation
  interpreter can leave that reference dead (datetime.strptime -> None),
  which crashed v0.0.1 browse (finding #1). Never use strptime in Kodi.
* service.py -- background service, 2s tick. BaseHandler carries TAG
  DEFENSE (internetradio's hard-won lesson: Kodi's ICY handling stomps
  updateInfoTag pushes; compare MusicPlayer.Title/Album InfoLabels vs
  last-pushed each tick, re-push on drift; push_tag builds on
  getPlayingItem() and sets album unconditionally so empty clears).
  - LiveHandler: port of internetradio's field-validated KexpHandler
    (plays/?limit=1, show-label cache, airbreak handling), minus
    history.
  - ArchiveHandler: the new trick. Session handoff gives sg_url,
    offset (sg-offset), file_start_epoch (= requested start - offset),
    show_label, art. One-shot seekTime(offset) executed from the
    service tick once getTotalTime()>0 (seeking inside onAVStarted is
    flaky; gives up to 0:00 after ~40s with a warning). Then every
    archive_poll seconds: broadcast moment = file_start_epoch +
    player.getTime(); query /v2/plays/?limit=1&ordering=-airdate&
    airdate_before=<moment UTC Z>; SANITY CHECK the returned airdate
    (must be <= moment and within 3h) -- if it fails, the filter is
    unsupported and we fall back to show-identity display with a loud
    log line instead of showing live metadata as archive metadata.
  - RadioPlayer._identify(): kexp_mode item property first; fallback
    matches getPlayingFile() against LIVE_STREAM_URL or the session
    file's sg_url (compared session-less, pre-'?', because the AIS
    redirect appends listeningSessionID). Log records which path won
    -- this answers the does-setResolvedUrl-preserve-properties
    question on first device run.
* Settings: live_poll (5-120s, def 20), archive_poll (5-60s, def 10),
  bitrate (64/128/256, def 128; label says effect unverified).
* Icon: generated placeholder (deliberately not the KEXP logo).

3. KEY API FACTS (full detail in kexp-archive-api.md)
================================================================================
get_streaming_url/?bitrate=N&timestamp=ISO -> {sg-url, sg-url-next,
sg-offset}. One MP3 file per show; files start ~10 min before the
nominal hour -- NEVER schedule math, always sg-offset. URLs stable/
deterministic/unsigned. StreamGuys host = AIS server, 302-wraps a
listeningSessionID (Kodi follows natively; never cache session URLs).
Files: audio/mpeg, Accept-Ranges bytes (native seeking), ~135 kbps for
bitrate=128. sg-url is IDENTICAL regardless of requested timestamp --
sg-offset is purely descriptive (seconds-into-file for the requested
moment); the CDN does NOT return a pre-positioned URL, redirect, or
scoped token, so there is no server-side way to open a stream already
seeked to an arbitrary point (see section 4b). v2 shows carry
start_time + program/host names + artwork; no end_time (show N ends at
show N+1's start). Plays are published first, annotated later (comment
arrives late -- internetradio lesson).

4. STATUS + FINDINGS (2026-07-21, v0.1.0 BETA)
================================================================================
ARCHIVE PLAYBACK IS VALIDATED END-TO-END ON DEVICE (the milestone). A
mid-show play was confirmed by ear + log + API cross-check:
  - Resolve -> identify -> seek -> sync chain all fire.
  - setResolvedUrl PRESERVES item properties: _identify() wins via
    "item property" (the session-file fallback is unused insurance, kept).
  - /v2/plays airdate_before filter WORKS (the load-bearing unverified API
    fact) and tracks the broadcast as playback advances.
  - Archive MP3s do NOT carry ICY -> no tag stomps (tag defense idle here).
  - ordering=-start_time on /v2/shows IS honored.

SEEK-SETTLE FIX (the one real playback bug, now fixed + validated):
ArchiveHandler used to declare the seek done the instant seekTime() was
called, but getTime() lags a tick or two, so the first sync read a stale
~0 position and anchored ALL later metadata ~30s early (and two runs of the
same show disagreed by up to a minute). Fix: split seek into REQUESTED vs
CONFIRMED -- after seekTime(), wait until getTime() is within
SEEK_CONFIRM_TOLERANCE (15s) of the offset before trusting the clock for
sync ("seek confirmed: position Ns ~= offset" log line). Validated: a 25-min
replay tracks 1:1 with wall clock, constant ~2-4s residual, no drift; songs
caught within single-digit seconds of their start.

TWO CONSTANT OFFSETS, both small, NEITHER drifts:
  1. OUR seek-settle error -- FIXED (was ~30s, now ~2-4s from poll timing).
  2. KEXP's play-logging lag -- INHERENT to their data (plays timestamped
     when the DJ logs them, not at airtime; ~minutes). Not fixable by us;
     same behavior as KEXP's own players. Documented, not a bug.

SORT CONVENTIONS (match KEXP): days grid descending (newest day first);
shows WITHIN a day ascending (earliest slot first, list_day sorts
start_epoch asc); Programs/DJs grids alphabetical (unique_programs/
unique_hosts); a program's or DJ's episode list stays date-descending
(inherited newest-first, matching KEXP's per-show "Episodes" order).

LOGGING (beta): routine browse traces (default.py trace()) and per-track
"tag pushed" + "onAVStarted fired" are LOGDEBUG now; INFO keeps the story
(attach, seek requested/confirmed, per-track archive sync line, warnings/
errors). Sync line kept at INFO through beta; demote later.

================================================================================
4b. SEEK-LAG INVESTIGATION -- CLOSED, NOT FIXABLE AT ADDON LEVEL (2026-08-10)
================================================================================
SYMPTOM: bookmark/resume and manual seeks confirmed working end-to-end
(archive audio resumes at the correct point), but seeking/resuming far
into a file is slow, and the delay scales with distance -- ~9s for a
~10-min jump (595s), ~50s for a ~47-min jump (2841s), both measured on
device via kodi.log.

DIAGNOSTIC METHOD: two full kodi.log captures (small seek, large seek),
then a third with Kodi's web server JSON-RPC enabled and full curl
tracing, to see actual HTTP-layer behavior around each seek.

RULED OUT (both original suspect theories):
  - Missing HTTP Range support -- FALSE. Every seek's "Resume from
    position N" log line is libcurl setting CURLOPT_RESUME_FROM, which
    issues a proper "Range: bytes=N-" request. Confirmed present in every
    capture.
  - Missing VBR seek index -- FALSE. KEXP confirmed archive files are
    genuinely CBR ("for precise time-offset calculations and reliable
    playback buffering" -- their words). The overshoot/EOF/backtrack
    pattern seen in early captures (seek to a huge byte offset, hit EOF,
    fall back near byte 0, re-probe) is NOT the seek itself -- it is
    Kodi's normal one-time file-open duration/EOF probing, which happens
    on every open regardless of target offset and finishes before any
    plugin-requested seek is even issued.

ROOT CAUSE (confirmed via full curl trace): once a stream is already
open, CDVDDemuxFFmpeg's seek to a plugin-requested time does NOT issue a
new byte-range HTTP request. It decodes and discards packets FORWARD,
over the network, from the current position to the target -- a decode-
forward walk, not a byte-jump seek. This is why lag is proportional to
distance: confirmed by zero new Range/GET requests appearing anywhere in
the multi-second-to-tens-of-seconds gap between the plugin's "seeking to
Ns" log line and ffmpeg's eventual "SeekTime - seek ended up on time N"
resolution.

WORKAROUND ATTEMPTED AND REJECTED: since bitrate is known (CBR, e.g.
256kbps => 32000 B/s), computed the target byte offset directly
(offset_seconds * 32000) and opened the stream pre-positioned via a Kodi
"|Range=bytes=N-" URL modifier, bypassing the open-at-0-then-seek
pattern entirely. HTTP layer worked perfectly (server returned 206
Partial Content immediately, correct Content-Range). BUT Kodi's
CFileCache does not know it opened into the middle of a larger resource
via this method -- it reads the partial response's Content-Length as if
it were the full local file size, then runs its normal near-end-of-file
probe against that wrong length, landing on a nonsensical position and
falling into a backward crawl in ~1024-byte decrements, reconnecting
each step, never converging within a 25+ second capture window. This is
WORSE than the original decode-forward stall, and confirms CFileCache's
seek bookkeeping has to go through Kodi's own native seek path to stay
consistent -- there is no clean way to hand it a pre-positioned URL from
outside that path.

ALSO CONFIRMED DEAD END: get_streaming_url's sg-offset is purely
descriptive; sg-url is identical no matter what timestamp is requested,
so there is no server-side mechanism to get a pre-positioned stream (see
section 3).

CONCLUSION: the bottleneck is inside Kodi/ffmpeg's own demuxer seek
implementation, not anything plugin.audio.kexp controls or can work
around from the Python side. INVESTIGATION CLOSED. No further seek-
lag work is planned -- accepted as a known limitation (documented in
README). Given how rarely a deep resume-at-checkpoint is expected on
this appliance, this is not worth further engineering time.

5. DEFERRED / KNOWN LIMITATIONS (documented in README, not blockers)
================================================================================
  - Deep-seek lag -- see section 4b. Investigated and closed; root cause
    is Kodi/ffmpeg player internals, out of addon scope.
  - sg-url-next continuation chaining (playback stops at file end); hook
    marked in onPlayBackEnded.
  - No archive listening history (open design question).
  - Manual seekbar absent in some skins' music OSD (file IS seekable;
    auto-seek to offset still works).
  - Schedule page (KEXP web has one; deferred as more complex -- forward-
    projected shows / grid view vs the archive's backward window).
  - bitrate variant unverified (64 vs 256 sg-url comparison would decide
    if the setting stays; currently a forgiving preference).
